# Design decisions

Decisions that the original specification left open, and choices made during the build.
Each has a one-line rationale. Changes agreed later are appended with the date.

## From the build brief

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | SBERT model `all-MiniLM-L6-v2` by default; the model name is a setting. | Fast on a laptop CPU with good semantic-similarity quality; can be swapped for `all-mpnet-base-v2` without code changes. |
| 2 | Cookie session auth (Flask-Login) + CSRF; same origin via Nginx (Docker) or the Vite proxy (local dev). | HttpOnly cookies keep credentials away from JavaScript; same origin avoids CORS and third-party-cookie problems. |
| 3 | Background jobs with RQ + Redis; progress by polling `GET /api/sessions/{id}` every 2–3 s. | Analysis takes tens of seconds and must not block HTTP workers; polling is simpler and more robust than websockets for this load. |
| 4 | Branched preprocessing: original-casing passages for NER, SBERT, BERTopic and evidence; a heavily normalised copy only for TF-IDF. | NER and transformer models rely on casing, punctuation and stop words; TF-IDF benefits from normalisation. A single linear pipeline would degrade one or the other. |
| 5 | Passages of 3–5 sentences (~100–200 words, configurable) are the unit of analysis, with document, page and position stored. | SBERT truncates long input; passages also give precise, citable evidence. |
| 5 | The dashboard counts library documents (not archived, not the NUC core) and recommendations of completed sessions. | The numbers planners act on. |
| 6 | Parse and split each document once (ingestion job), store passages and embeddings, reuse across sessions. | Avoids repeating the slowest work and makes session runs fast and consistent. |
| 7 | Candidate topics are BERTopic topics over non-NUC passages only; topic −1 (outliers) is discarded. | The NUC core is the baseline being compared against, not a source of new topics. |
| 8 | Candidate embedding = L2-normalised mean of member passage embeddings. | A standard, cheap topic centroid in the same space as the passage embeddings. |
| 9 | Novelty = 1 − max cosine similarity to any NUC core passage (clipped to [0,1]); `max_sim > 0.80` → "Potential Duplicate". The closest NUC passage id is stored. | Max similarity catches a candidate duplicated by any single part of the core; storing the passage lets planners verify side by side. |
| 10 | Skill score = log1p(sum of document frequencies of the candidate's top skills), min-max normalised across candidates (all equal → 1.0). | Document frequency rewards skills demanded by many sources rather than one repetitive advert; log damps outliers. |
| 11 | Theme score = (topic passages / non-outlier passages) × mean topic probability, min-max normalised. | Combines how prevalent a theme is with how confidently passages belong to it. |
| 12 | Composite = 0.40·skill + 0.35·theme + 0.25·novelty (weights per session, sum 1.0 ± 0.001); top 20 kept; duplicates kept and badged. | Weights from the project specification; planners, not the system, decide on duplicates. |
| 13 | Titles auto-generated from top c-TF-IDF keywords; planners can edit (`auto_title` and `topic_title` stored separately). | Gives a readable default while preserving the machine output for audit. |
| 14 | `RecommendationEvidence` table with the top 8 representative passages per topic and a relevance score. | Makes every recommendation traceable to its sources. |
| 15 | Reports as PDF (primary, WeasyPrint) and DOCX (python-docx). | PDF for circulation; DOCX for committee editing. |
| 16 | Uploaded files stored on a Docker volume under UUID names; original filename kept in the DB. | Prevents path traversal and name collisions; files never served from a public path. |
| 17 | Documents used by a session cannot be hard-deleted (409), only archived; users are deactivated, never deleted. | Keeps past sessions and the audit trail reproducible. |
| 18 | Exactly one active NUC core version, uploaded by admins; each session records the version it used; sessions cannot run without one. | Results must be reproducible against a known baseline. |
| 19 | The 30% credit-unit allowance is an admin setting, null until set. | The figure varies by institution and programme; no number is assumed. |

## Made during the build

| Phase | Decision | Rationale |
|-------|----------|-----------|
| 0 | **Pydantic v2** (not Marshmallow) for request/response validation. | Type-hint based schemas match the typed backend and give clear validation errors for the 422 envelope. |
| 0 | Postgres image `pgvector/pgvector:pg16`; passage embeddings will use a pgvector `vector(dim)` column. | Official PostgreSQL 16 plus the pgvector extension; stores embeddings natively instead of float arrays. |
| 0 | Environment chosen by `APP_ENV` (`development`/`testing`/`production`); production refuses to start without a strong `SECRET_KEY`, `DATABASE_URL` and `REDIS_URL`. | `FLASK_ENV` is deprecated; failing fast prevents insecure deployments. |
| 0 | `GET /api/health` returns 200 when Postgres and Redis are reachable, otherwise 503 with per-service results. | Gives the UI, Docker and monitoring one reliable signal. |
| 0 | In Docker development, Nginx is the single entry point (`http://localhost:8080`): `/api` → Flask, everything else → Vite dev server (with HMR websocket). | Same origin as production, so cookie and CSRF behaviour is identical in development. |
| 0 | Frontend uses current majors: React 19, Vite 8, React Router 8, Tailwind 4, TypeScript 6, ESLint 10, Vitest 5; shadcn/ui on the Radix base. | Scaffolded with the official `create-vite` template so the versions are known to work together. |
| 0 | Branches: `main` (releases), `develop` (integration), `feature/<phase>`. | As specified in the brief. |
| 0 | Lightweight dev mode: `docker-compose.services.yml` runs only Postgres and Redis; the full `docker-compose.yml` `include`s it; both share the project name `nlprs`. | Lets the app run natively on slow machines, with one definition of each service and shared data volumes. |
| 0 | Backend tests use a separate `<db>_test` database on the same server, created automatically; the suite refuses any database not named `*_test`. SQLite is not used for tests. | The models need PostgreSQL features (JSONB, pgvector), and development data must never be touched. |
| 0 | Exact dependency pins everywhere: exact versions in `package.json` plus the committed npm lockfile; pip-tools lockfiles (`requirements*.txt`) compiled from `requirements*.in` for Python 3.11/Linux. | Reproducible builds for examiners and deployment. |
| 1 | The session cookie holds a per-user random `session_token`, not the user id. The token is rotated on password change, password reset and deactivation. | Those events then end every existing session of the user immediately, even though Flask's signed-cookie sessions are stored client-side. |
| 1 | Sessions last 8 hours. Logout clears the cookie; the token itself is not rotated at logout, so logging out on one device does not end the user's other sessions. | Standard behaviour for multi-device use; forced sign-out everywhere is available by resetting the password. |
| 1 | CSRF via Flask-WTF: the token lives for the whole session, is sent in `X-CSRFToken`, is rotated at login and logout (and returned in the response), and the frontend refreshes it and retries once on `CSRF_FAILED`. | Protects every state-changing request, including login, without making long-lived browser tabs fail. |
| 1 | Login accepts a username or an email, case-insensitively. Unknown users and wrong passwords get the same message, and bcrypt still runs for unknown users; "account deactivated" is only revealed after a correct password. | Prevents discovering which accounts exist by comparing messages or response times. |
| 1 | Passwords: at least 8 characters and at most 72 bytes (bcrypt's input limit; longer passwords are rejected, not silently truncated). bcrypt cost 12, and 4 in tests. | Meets the brief's minimum length and avoids bcrypt's silent truncation. |
| 1 | Admins cannot change their own role or deactivate themselves. | Guarantees at least one active admin always remains. |
| 1 | Enumerations are stored as VARCHAR with CHECK constraints, not native PostgreSQL enum types. | Adding a value later is a one-line migration. |
| 1 | `Passage.embedding` is a dimension-less pgvector `vector`, plus an `embedding_model` column. | The SBERT model is a setting; different models produce different dimensions, and mixed embeddings are detectable. Similarity is computed in Python over small sets, so no vector index (which needs a fixed dimension) is required. |
| 1 | Columns added beyond the brief: `users.session_token`, `passages.embedding_model`, `recommendations.topic_id` and `created_at`, `reports.error_message` and `completed_at`. | Needed for session invalidation, embedding provenance, traceability to BERTopic topics and report-job failures. |
| 1 | `skill_patterns.pattern` is JSONB holding either a phrase string (matched case-insensitively) or a spaCy token pattern list. Short, ambiguous names (Go, R, C) use token patterns that require a confirming next word, e.g. "Go developer". | One column supports both EntityRuler pattern styles, and avoids false matches such as "go to the office". |
| 1 | The seed data has 172 canonical skills (302 patterns including aliases) and 81 domain stop words; `flask seed` is idempotent. | Exceeds the ~150 skills asked for; re-running the seed is safe. |
| 1 | Rate limiting of login is left to Phase 6. | Follows the phase plan in the brief. |
| 1 | Tests build the `_test` database with the real Alembic migrations, and empty the tables after each test with DELETE. | The migrations themselves get tested; DELETE is much faster than TRUNCATE for small tables. |
| 1 | In Docker development, Nginx re-resolves container names through Docker's DNS, and the frontend container reinstalls `node_modules` automatically when `package-lock.json` changes. | Recreated containers and newly added packages then work without manual restarts or volume resets. |
| 2 | Uploads with exactly the same content (SHA-256, stored in the new `documents.content_hash` column) as a non-archived document are rejected. | Duplicate job adverts would inflate keyword, skill and theme scores. |
| 2 | The frontend uploads one file per request, even though the API accepts several. | Gives a real progress bar and an accept/reject result for each file. |
| 2 | Content-type checking uses libmagic (python-magic) plus each format's own signature (PDF header, DOCX zip containing `word/document.xml`, no NUL bytes in text). Without libmagic (native Windows), the signature checks run alone and a warning is logged. | libmagic is available in Docker/production; native Windows development still gets strict checks. |
| 2 | Header/footer removal: a line counts as a header/footer only if it is among the first or last 2 lines of a page, has at most 12 words, and repeats (digits ignored) on more than half the pages of a document with 3+ pages. | Removes running headers and "Page n of N" lines without ever deleting repeated body text. |
| 2 | Bullet items and short headings get a full stop during light cleaning. | Otherwise job-advert lists merge into one long run-on "sentence". |
| 2 | Passages: 3–5 sentences; closed once they reach 3 sentences and 100 words, 5 sentences or 200 words. Sentences over 200 words are cut into chunks; a final fragment (under 3 sentences and 50 words) joins the previous passage. A passage's page is its first sentence's page. | Follows decision 5 while keeping every passage within the SBERT input limit. |
| 2 | TF-IDF normalisation keeps technology tokens such as "C++", "Node.js" and "HTML5" (spaCy's URL detector is not used, since URLs are removed during cleaning); tokens shorter than 2 characters are dropped. | Keeps meaningful skill terms for TF-IDF. Single-letter languages (C, R) are still captured by the NER patterns in Phase 3. |
| 2 | TXT decoding order: UTF-8 (with/without BOM) → Windows-1252 → charset-normalizer → Latin-1. | The corpus is English-only; non-UTF-8 files are almost always Windows-1252, which is more reliable than guessing. |
| 2 | The RQ worker is a `SimpleWorker` (jobs run in the worker process; `restart: unless-stopped` in Docker), with timer-based job timeouts on Windows. | spaCy and SBERT stay loaded between jobs (first job ~40 s, later ones under 1 s) and PyTorch is never forked. |
| 2 | A NUC core version becomes active when its document is ready, unless a newer version is already active; a failed upload leaves the previous version active. `GET /api/nuc-core` is readable by every role; only admins upload. | Planners need to see whether sessions can run; there is always a usable baseline. |
| 2 | Archiving is allowed only for ready or failed documents; NUC core documents cannot be archived or deleted from the library. There is no un-archive yet. | Avoids racing the ingestion job and removing the active baseline. |
| 2 | Opt-in `USE_SYSTEM_CERTS=true` makes Python (and `scripts/lock.py`) verify HTTPS against the operating-system certificate store (truststore). | Antivirus HTTPS scanning (Avast Web Shield on the development laptop) otherwise breaks model downloads; nothing extra is trusted. |
| 2 | Python lockfiles are generated with uv (`scripts/lock.py`) for Linux / Python 3.11, with PyTorch from its CPU-only index; numpy is pinned to 2.4.6 (2.5 needs Python 3.12). | Reproducible Docker installs without ~3 GB of CUDA libraries; runs natively without Docker. |
| 2 | `app/config.py` loads the repository `.env` before reading settings (existing environment variables win). | Every entry point (flask CLI, native worker, tests) sees the same configuration; previously the native worker missed `.env`. |
| 3 | A session's `parameter_config` is a snapshot of the default settings (plus the planner's overrides) taken at creation. | Re-reading a session always shows exactly how it was configured, even after admins change the defaults. |
| 3 | Only `pending` sessions can be run and only `failed` ones retried (a retry clears the previous results); completed sessions are not re-run, and running sessions cannot be deleted. | Keeps planners' decisions attached to the results they were made on; a new analysis is a new session. |
| 3 | Running requires an active NUC core: checked when the run is requested (409 `NO_NUC_CORE`) and again in the job's validating stage. | Immediate feedback, and no race if the core changes in between. |
| 3 | Skill demand uses the document frequency of each of the candidate's top 10 skills across **all documents in the session** (decision 10 read as corpus-wide demand), then log1p and min-max. | Measures how widely a skill is demanded in the sources, not only within the theme. |
| 3 | Skills are the EntityRuler matches only (entities carrying a pattern id); the statistical NER labels (ORG, GPE, spaCy's own LANGUAGE, ...) are ignored. The ruler runs before `ner` on a pipeline without parser/tagger/lemmatiser. | Avoids counting company or place names as skills; faster. |
| 3 | BERTopic clusters the SBERT embeddings of the original text, while topic words (c-TF-IDF) come from the normalised text; UMAP (`n_neighbors ≤ 15`, 5 components, cosine, `random_state=42`, single-threaded) + HDBSCAN (`min_cluster_size = min_topic_size`). At least `max(2 × min_topic_size, 10)` passages are required; a run where every passage is an outlier fails with an explanation. | Meaningful clusters with readable lemma keywords, repeatable runs, and clear failures on tiny corpora. |
| 3 | Theme strength uses BERTopic's HDBSCAN membership probability per passage (`calculate_probabilities=False`). | This is the "topic probability" of decision 11 without the cost of full probability matrices. |
| 3 | Evidence relevance = cosine similarity between a passage and the topic centroid; the top `evidence_per_recommendation` passages are stored. | The most representative passages are the best evidence. |
| 3 | Titles: top c-TF-IDF terms compared by Porter stem (NLTK; spaCy has no stemmer), preferring two-word phrases, joining separately ranked words of a known skill ("machine" + "learn" → "Machine Learning"), skipping generic job-advert words and repeated stems; skills use their canonical spelling. | Produces titles such as "Machine Learning, Model and AI" instead of "Machine, Learn and Learning". |
| 3 | All candidate themes are kept in the topics/similarity results; only the top `max_recommendations` become Recommendation rows. Ties in composite score go to the larger theme. | The Evidence Dashboard shows every theme; the review list stays focused. |
| 3 | `analysis_sessions.stage_timings` stores seconds per stage (migration `0003`). | Shown in the stage tracker and used to check the performance target. |
| 3 | Benchmark (`python -m evaluation.benchmark_pipeline`, synthetic 20 × 3,000 words): session analysis 43.6 s on the first run in a fresh worker (≈34 s of that is one-off UMAP/numba compilation) and ~10 s warm, on the development laptop CPU. | Meets the ≤ 60 s target (decision/brief §6.2). |
| 4 | A decision can be changed or cleared (`decision: null` returns it to undecided) at any time, except while the recommendation is mapped to a course: then only `accepted` is allowed. | Planners can correct mistakes, and the proposed curriculum never contains a rejected or flagged topic. |
| 4 | One course per recommendation; only accepted recommendations can be mapped. Course codes follow the NUC style (2–4 letters + 3 digits, optional letter), are stored normalised (`CSC 419`) and are unique within a session. Credit units are 1–3; 1–15 learning outcomes are required. | Keeps the proposed curriculum consistent and comparable with CCMAS course listings. |
| 4 | The recommendations list is not paginated, and its review counts always cover the whole session regardless of filters. | It is bounded by `max_recommendations` (≤ 100); the "x of N reviewed" progress must not change with the filter. |
| 4 | Evidence results are the stored session payloads, enriched at read time with document titles, NUC passage page numbers and the NUC core version label. | Titles can change after a run; nothing is duplicated in the stored results. |
| 4 | Charts follow a validated palette: one blue hue for magnitude, the reserved warning amber (with an icon and the words "Potential Duplicate") for themes above the threshold, thin 16 px bars from one baseline, hover tooltips, and a table beside every chart. The Evidence route is lazy-loaded. | Readable and colour-blind safe (checked with a palette validator); nothing is conveyed by colour alone; the chart library (~380 kB) loads only on that page. |
| 4 | The review screens are session sub-pages (`/sessions/{id}/evidence`, `/recommendations`, `/curriculum`) with their own links, rather than new sidebar items. | Every screen is about one session; the sidebar stays short. |
| 5 | Reports are built once as a format-neutral document (sections of paragraphs, key/value lists, bullet lists and tables) and then rendered to PDF (HTML + WeasyPrint) or DOCX (python-docx). | Both formats always contain the same content, and the content can be unit-tested without rendering. |
| 5 | Report sections: corpus summary, NLP findings, overlap, recommendations, decisions and proposed courses, always in that order, with a cover (session, NUC core version, weights, threshold, generation time) and a decision-support disclaimer. Reports reflect decisions and mappings at generation time. | Matches the brief's section list; the disclaimer states that planners, not the system, decide. |
| 5 | Report files live in `STORAGE_DIR/reports/` under UUID names, are downloaded only through `GET /api/reports/{id}/download`, and are deleted with their report or session. Reports can be deleted (not while generating). | Decision 16; no orphaned files on the volume. |
| 5 | WeasyPrint needs Pango, which the Docker image installs. Where it is missing, PDF reports fail with a clear message and DOCX still works; the real-PDF test is skipped there. | Native Windows development lacks Pango; the failure is explicit, not silent. |
| 5 | Settings are updated partially (`PUT` with any subset), validated per key, and audited with old and new values. The spaCy pipeline must be installed; the SBERT model name is only syntax-checked (it downloads on first use). | Prevents unusable settings while keeping model choice open. |
| 5 | Changing the embedding model does not re-embed existing documents; sessions whose documents or NUC core were embedded with different models fail at the loading stage with an explanation. | Mixed embeddings are not comparable; re-embedding everything silently would be slow and surprising. |
| 5 | Active stop words are also removed from the stored normalised text at analysis time, not only at ingestion. | Stop words added later take effect in new sessions without re-uploading documents. |
| 5 | Skill patterns and stop words are deactivated, never deleted. Phrase patterns are unique per label case-insensitively; token patterns are validated by spaCy's EntityRuler. | Keeps the history of what earlier sessions used; readable errors for invalid patterns. |
| 5 | The audit log filter `action` accepts an area (`auth`) or an exact action; dates are UTC days. The CSV export (≤ 100,000 rows) neutralises formula-like cells and is itself audited. | Useful filtering without a second parameter; safe to open in spreadsheets. |
| 6 | Passage grouping (refines decision 5): the 5-sentence limit closes a passage only once it has at least half the minimum words (50); otherwise passages close at 3+ sentences and 100+ words, or 200 words. | The real CCMAS document lists course contents as fragments ("Capacitance. Electric dipoles. ..."); a strict 5-sentence cap gave a median of 43 words per passage (1,548 passages), too little text for reliable embeddings. Now: median 66 words (1,000 passages); the policy document 72 → 90. |
| 6 | Theme strength (refines decision 11) is document-weighted: each passage weighs 1 / (passages in its document), so `strength = (weighted passages in the theme / weighted non-outlier passages) × mean probability`. | On the real corpus one policy PDF (116 passages) formed a 102-passage theme with strength 1.0 and ranked #1, squashing every job theme to 0.00–0.27. Every document now counts equally. Approved by the project owner. |
| 6 | Course-level overlap (refines decision 9): at ingestion the NUC core is split into courses (header "CODE NNN: Title (N Units ...)", content up to the next header, at most 500 words; a repeated code keeps its longest description). Each course gets one embedding: the L2-normalised mean of the SBERT embeddings of its 200-word chunks. Themes are compared with every course; `max_sim`, novelty and the duplicate status (threshold 0.80, strict) come from the closest course, whose id is stored (`recommendations.closest_nuc_course_id`). The closest passage is still stored for side-by-side evidence. A core with no recognisable courses falls back to passage-level comparison. `flask extract-courses` backfills existing cores. | A single NUC passage is often a fragment of a course outline, so passage similarity says little about whether a theme is already taught. Planners think in courses ("Closest NUC course: SEN 304 – Software Testing & Quality Assurance"). On the real CCMAS: 118 courses, 82–500 words (median 181). The 0.80 threshold is kept for now and calibrated on labelled theme–course pairs in the evaluation. Approved by the project owner. |
| 6 | Generic NUC courses are excluded from the overlap comparison: the admin setting `nuc_course_exclusions` lists course-code prefixes (default `GST`) and title keywords (default SIWES, Industrial Work Experience, Industrial Training, Final Year Project, Seminar), matched case-insensitively. Exclusions apply when a session runs (no re-upload needed); the similarity results record how many courses were compared and excluded, and the NUC Core page lists every course with "Excluded from comparison" where it applies. ENT courses are kept. | On the real corpus, SIWES and Final Year Project descriptions (work experience, reports, communication) were the closest "course" for 5 of the top 20 themes although they teach no subject content. The defaults exclude 32 of the 118 CCMAS courses and keep INS 401 Project Management. Approved by the project owner. |
| 6 | Scores are computed and stored as 0–1 decimals but shown to people out of 100: the composite as "Score 85/100", sub-scores as points with High (70+) / Medium (40–69) / Low (<40), weights as "counts for 40%", contributions as whole points (largest-remainder rounding so the parts add up to the total), similarities as percentages. The exact decimal calculation stays behind "Show calculation"; the recommendations CSV carries both. Reports use the same presentation. TF-IDF keyword weights stay decimal (relative term weights, not scores). | Planners found decimals such as 0.62 hard to read; points and levels are easier to compare and explain, while the exact values remain available for the evaluation and the examiner. Requested by the project owner. |
| 6 | Skill demand is specificity-weighted and theme strength square-rooted (refines decisions 10 and 11): skill demand = `log1p(Σ document frequency × share of the skill's mentions that fall in this theme)` over the theme's top skills, min-max over the themes that have skills (themes without skills score 0); theme strength = the document-weighted value, square root, then min-max. Weights and novelty unchanged. Full before/after comparison: [SCORING_COMPARISON.md](SCORING_COMPARISON.md). | On the real corpus 20 of 31 themes had a skill score of 0.80 or more, because common skills (Agile, Linux, SQL, communication) lifted every theme, and the median theme strength was 0.15 because the largest theme set the maximum. After the change: skill median 0.60 (was 0.84), theme median 0.34 (was 0.15); specific themes rise (React/.NET #13 → #4, the security themes #14/#11 → #5/#6), generic ones fall (Unix/Linux #8 → #16), and the largest theme keeps #1 with a 7-point lead instead of 17. Rank scaling (B) and log/rank theme scaling were rejected: they ignore gap sizes and let a theme with no skills into the top 20. Approved by the project owner. |
| 6 | Lecturer workflow: the decision "flagged" is shown as "Discuss later" (stored value unchanged); a recommendation card shows Accept / Reject / Discuss later only while undecided, then the status with a "Change decision" link; accepted topics lead to "Design course" (the former "Map to course"; "Proposed Curriculum" is now "Proposed courses"). Every session page shows the steps Review → Design courses → Report with live counts (`GET /api/sessions/{id}/progress`) and a next-step banner. The one-click "Download report" generates a **Word (DOCX)** report with every section and downloads it when ready; PDF and section choices sit under "More options" (refines decision 15: PDF stays available and is the format of record in Docker). One-click decisions keep existing notes. | Requested by the project owner after watching the review flow: after accepting, the dark Accept button read as "still needs accepting" and the next step (designing the course) was not visible. DOCX is the default because it opens everywhere and needs no system libraries (PDF needs Pango, missing natively on Windows). |
| 6 | Near-duplicate topics are merged after clustering: repeatedly join the two topics whose centres (L2-normalised mean embedding of their extracts) are most similar while that similarity is above **0.83** (average linkage), then let BERTopic recompute the merged topics' words (`merge_topics`). Merged groups are recorded in the topics results. | On session 10 the same topic appeared twice (#5/#6, security; centre similarity 0.842) and three policy topics were near-copies (0.847, 0.841). The next pair was 0.813 (median of all pairs 0.45), so 0.83 sits in a clear gap; 0.85 would have missed the security pair. Before/after in SCORING_COMPARISON.md. Requested by the project owner. |
| 6 | Topics get course-style names from a curated, admin-editable catalogue (setting `topic_name_catalogue`, 120 names from ACM/IEEE CS2023 knowledge areas and common NUC course titles). Similarity = average of cos(topic centre, name) and cos(topic keywords as a phrase, name), SBERT; the best name is used if the similarity is **≥ 0.50**, names are unique (the closer topic wins; the other takes its next name above 0.50 or keeps its keyword title). Keywords are shown under the title ("Keywords: …"); planner edits still override (`topic_title`), the machine name stays in `auto_title`. | Keyword titles ("Project, English and Problem") confused lecturers. On session 10 names at 0.50 and above were right (e.g. "IT Service Management (ITIL)" at 0.50, "Threat Intelligence and Vulnerability Management" at 0.70) and below it wrong or vague ("Broadband Penetration…" → "IT Infrastructure Management" at 0.47); 25 of 28 topics are named. The centre alone favoured generic names, the keywords alone missed context; the average worked best. Requested by the project owner. |
| 6 | Descriptions are plain: "Why this is recommended: M of the N documents mention this area, mostly {document type} for roles such as “…” and “…”. Employers ask for skills in {top 5 skills}." The most representative extract is shown separately as "Example from a {type} ({title, source, month year}): “…”". Keyword lemmas are shown as written in the documents (the most frequent written form of each lemma phrase: "problem solving", not "problem solve"); repeated or contained single words are dropped. | "A theme found in 41 passages… centred on…" was jargon, and lemmas ("Problem Solve") read as mistakes. Requested by the project owner. |
| 6 | Documents carry a source, the original link and the publication date (migration 0005), set from the collector's manifest (`flask import-manifest`) or edited on Document Detail. Everywhere a document is referenced (evidence, examples, topic samples, reports) it reads "Title, type (source, Mon YYYY)", e.g. "Senior QA Engineer – Hydrogen, job advert (MyJobMag, Sep 2026)", never the file name. Plain terms throughout the UI and reports: topic (theme), extract (passage), employer demand (skill demand), how often it comes up (theme strength), how new it is (novelty), "Not in NUC core" / "May already be in NUC core"; the technical names stay in "Show calculation", the docs and this file. Before/after of the main wording: PLAIN_LANGUAGE.md. | The users are lecturers without a computing background; file names such as "myjobmag_cybersecurity_…_2026-09-18.txt" and NLP terms made the evidence hard to trust. Requested by the project owner. |
| 6 | HDBSCAN uses `min_samples = min(3, min_topic_size)` instead of its default (`min_samples = min_cluster_size`). | On the real corpus the default was unstable: 2 to 23 themes depending on the UMAP seed, and adding 5 adverts turned 17 themes into 4 (one theme holding 70% of the passages). With 3: 26–33 themes on every seed and corpus tested, largest theme 41–66 passages, 9–16% outliers. The top `max_recommendations` (20) are kept. |
| 6 | Light cleaning for justified PDF text: headings are only recognised at paragraph boundaries and never when a line ends with a connector word; bullet items end at the next bullet, a paragraph boundary, or a capitalised line (unless the item's line ends with a connector or has only one or two words); a bullet marker alone on its line starts the next item; table-of-contents dot leaders are removed. | The real policy PDF breaks lines mid-sentence and list items one word per line, which previously produced fragments such as "Communications and Digital. Economy". |
